# Java Blueprints — визуальная среда программирования

Веб-инструмент для кейса Axenix: загружает Java-монолит, показывает его как граф
(обзор классов и вызовов + блок-схема каждого метода), находит дефекты с оценкой Big O,
позволяет править программу из графа или из кода (синхронизация в обе стороны)
и автоматически проверяет, что поведение после изменений сохранилось.

## Запуск

### Что нужно установить

| Что | Зачем | Обязательно |
|---|---|---|
| Node.js 20+ и pnpm | сервер и клиент | да |
| JDK 17+ (`javac`, `java` в `PATH` или `JAVA_HOME`) | компиляция, запуск, сравнение поведения | да |
| Maven 3.9+ (`mvn` в `PATH` или `MAVEN_CMD`) | проекты с `pom.xml`, библиотеки проектов без него (JavaFX, Gson…), Mockito для тест-кейсов классов | для этих функций |
| [Ollama](https://ollama.com) с моделью (по умолчанию `qwen2.5:14b-instruct`) | тест-кейсы от локальной LLM | нет: без неё работают эвристики |

Проверить окружение: `node -v`, `pnpm -v`, `javac -version`, `mvn -v`, `ollama list`.

### Первый запуск

```bash
pnpm install           # корень: concurrently
pnpm install:all       # зависимости server/ и client/; postinstall генерирует клиент Prisma
pnpm dev               # миграции SQLite, сервер :3001 и клиент :5173
```

Откройте http://localhost:5173 и выберите «Открыть пример», «Импорт проекта» (папка целиком) или «Импорт .java».
Первая сборка Maven-проекта и первые тест-кейсы классов скачивают зависимости в `~/.m2` — это до нескольких минут,
дальше быстро.

Другие команды:

```bash
pnpm typecheck         # проверка типов сервера и клиента
pnpm build             # сборка клиента в client/dist
pnpm -C server start   # сервер без перезапуска при правках
pnpm -C server db:studio  # просмотр базы настроек
```

Клиент на :5173 проксирует `/api` на сервер :3001, поэтому в dev-режиме нужны оба процесса — `pnpm dev`
запускает их вместе.

## Пользовательский путь

1. **Загрузить** — «Импорт проекта» (папка целиком, пути пакетов и `pom.xml` сохраняются), «Импорт .java»
   или «Пример». Тесты из `src/test` пропускаются. Загруженная версия фиксируется как **эталон**.
2. **Разобрать** — сервер строит AST (tree-sitter-java), модель классов, граф вызовов и находит приложения
   (модули Maven, классы с `main`, `@SpringBootApplication`) и связи между ними (HTTP, Feign, брокеры).
3. **Смотреть на трёх уровнях** (вкладки над графом):
   - «Приложения» — сервисы проекта и связи между ними (только если приложений несколько);
   - «Границы» — классы внутри рамок своих приложений и вызовы через границы;
   - «Методы» — обзор классов (методы, вызовы, сложность, число проблем) и блок-схема метода.
4. **Исследовать и править**:
   - клик по узлу ↔ подсветка кода; клик в коде → выбор метода и узла;
   - двойной клик по узлу — редактирование его кода (Enter — применить, Shift+Enter — перенос, Esc — отмена);
   - палитра «Блоки» — вставка после выбранного узла (или в начало метода), «Удалить выбранный блок»;
   - правка в редакторе кода сразу перестраивает граф;
   - панель проблем справа: дефекты, Big O и места, где программа зависит от окружения; клик ведёт к коду.
5. **Распилить** — вкладка «Распил»: варианты разбиения на микросервисы с оценкой и «Узкие места» монолита;
   «к коду» и строки подробностей выделяют место в панели кода.
6. **Тест-кейсы** — нижняя панель: stdin-тесты программы и тест-кейсы класса или метода (эвристики + локальная LLM,
   заглушки зависимостей через Mockito); кейсы можно править.
7. **Собрать и сравнить** — «Экспорт» скачивает текущие файлы, «Запуск» компилирует и выполняет на первом тесте,
   «Проверить поведение» запускает эталон и текущую версию на одинаковых входах: stdout, stderr и код выхода,
   а для тест-кейсов классов — результаты вызовов должны совпасть. Spring Boot- и JavaFX-приложения по stdin
   не запускаются (им нужны БД или окно), для них сравниваются тест-кейсы классов.

## Архитектура

```
client/ (Vite + React 19 + TS)               server/ (Node + Express 5 + TS, tsx)
├─ components/AppsView     приложения        ├─ parser.ts      web-tree-sitter + tree-sitter-java (wasm)
├─ components/BoundaryView границы           ├─ model.ts       классы, поля, методы, граф вызовов по типу получателя
├─ components/ClassView    обзор классов     ├─ cfg.ts         блок-схема метода (CFG) с диапазонами исходника
├─ components/FlowView     блок-схема        ├─ analyzer.ts    правила, метрики, Big O; streams.ts — Stream API
├─ components/DecomposeView распил           ├─ perf.ts        правила Spring/JPA (N+1, транзакции, прокси)
├─ components/CodeEditor   Monaco            ├─ services.ts    приложения и связи между ними
├─ components/AnalysisPanel проблемы         ├─ decompose.ts   варианты распила; bottlenecks.ts — узкие места
├─ components/BottomPanel  консоль/тесты     ├─ runner.ts      javac/Maven/java в temp-каталоге, diff поведения
├─ components/CasesPanel   тест-кейсы классов
├─ components/SettingsDialog                 ├─ libs.ts        библиотеки проектов без pom.xml по импортам
├─ project.ts              импорт папки      ├─ cases.ts       тест-кейсы: эвристики + Ollama
└─ edits.ts                правки по Range   ├─ units.ts       прогон тест-кейсов (JbpRuntime + Mockito)
                                             ├─ scope.ts       зависимость от окружения (потоки, время, сеть…)
                                             ├─ store.ts       настройки и проекты (Prisma + SQLite)
                                             └─ index.ts       REST API
shared/types.ts — общие типы; examples/OrderApp.java — демо-монолит
```

**Ключевая идея синхронизации.** Граф — это проекция AST, а не отдельная модель.
Каждый узел хранит диапазон исходника (`range` — редактируемая часть, `stmtRange` — весь оператор,
`code` — точный текст). Правка в графе — это точечная замена текста по диапазону; после неё код
заново анализируется, и граф строится заново. Поэтому граф и код не могут разойтись, а форматирование
и комментарии вне правки сохраняются. Пока анализ не догнал правку, редактирование из графа блокируется.

### Распил на микросервисы

Вкладка «Распил» строит граф зависимостей классов приложения. Веса связей: наследование и generic-аргументы 4,
поле 3, вызов метода 1, тип параметра или результата 1. Роли классов (сущность, репозиторий, контроллер,
слушатель, сервис, DTO, конфигурация) определяются по аннотациям Spring/JPA и имени. Конфигурация и точка входа
копируются в каждый сервис и в распил не входят. Способы разреза:

- **По сущностям** — агрегат: `@Entity` и то, чем она владеет (`@OneToMany`, `@OneToOne`, `@Embedded`,
  `@ElementCollection`). К агрегату добавляются его репозиторий и классы с тем же доменным именем, остальное
  притягивается по силе связей.
- **По API** — группы контроллеров и слушателей с общим доменным именем.
- **По связности** и **Крупные сервисы** — сообщества графа (Louvain, разрешение 1 и 0.5). Классы с общим
  доменным именем (`Order`, `OrderController`, `OrderService`…) кластеризуются вместе, иначе алгоритм режет по слоям.
- **По пакетам** — только если пакеты функциональные. Слоистые пакеты (`controller`, `service`, `repository`…)
  дали бы распределённый монолит, поэтому такой вариант не предлагается.

DTO и исключения, которыми пользуются несколько сервисов, выносятся в общий модуль. Для каждого варианта
считаются: доля связей внутри сервисов, модулярность (Newman), циклы между сервисами (Тарьян), сущности, нужные
другим сервисам, доля кода в самом крупном сервисе, а также список вызовов, которые после распила станут
API или событиями. Оценка 0–100 — эвристика: 50 × связность + 50 × модулярность/0.6, минус 12 за цикл, 5 за
общую сущность, 6 за каждую транзакцию, которую разрез делает распределённой (не больше 18), 20 если один сервис
содержит больше 70% кода. Приложение меньше 8 связанных классов не режется.

#### Узкие места монолита

Раздел «Узкие места» на той же вкладке; клик по пункту подсвечивает затронутые классы на графе.
«к коду» выделяет главное место в панели кода: вызов, замыкающий цикл, объявление класса или метода;
строки подробностей ведут к своим местам (дефект на пути запроса, вызов из чужого домена, поле с репозиторием).
Считается и для приложений, которые не режутся.

| Вид | Признак |
|---|---|
| Тяжёлый эндпоинт | на пути запроса (граф вызовов, до 6 шагов) есть дефекты производительности из таблицы ниже или данные 3+ агрегатов |
| Транзакция через агрегаты | `@Transactional` (не `readOnly`) меняет данные 2+ агрегатов, с учётом вызываемых методов; при распиле — сага или outbox |
| God-класс | работает с 4+ доменами, или с 3, если класс большой (300+ строк или 20+ методов) либо у него 5+ зависимостей. Домен — имя, у которого есть сущность, контроллер или слушатель |
| Общие данные | агрегат, с таблицами которого (через сущности и репозитории) работают 2+ чужих домена |
| Центральная зависимость | класс с логикой, которым пользуются классы 3+ модулей |
| Цикл между доменами | сильно связная компонента графа классов из 2+ доменов (связи сущность↔сущность не в счёт) |

### Диагностика

| Правило | Что ищет | Оценка |
|---|---|---|
| `nested-loops` | вложенные циклы; если внутри поиск по равенству — советует индекс HashMap | O(nᵏ) → O(nᵏ⁻¹) |
| `linear-search-in-loop` | `contains/indexOf/remove` у List внутри цикла | O(n²) → O(n) |
| `string-concat-in-loop` | `s += …` для String в цикле | O(n²) → O(n) |
| `empty-catch` | пустой catch | — |
| `long-method` | > 40 строк (> 80 — высокая) | — |
| `high-cyclomatic` | цикломатическая сложность > 10 | — |
| `duplicate-block` | одинаковые блоки из 3+ операторов | — |
| `stream-sort-for-min` | `sorted(…)…findFirst()` ради одного элемента → `min(…)` | O(n log n) → O(n) |
| `stream-count-for-exists` | `count() > 0` / `== 0` → `anyMatch` / `noneMatch` | — |
| `stream-find-is-present` | `filter(…).findFirst().isPresent()` → `anyMatch` | — |
| `stream-foreach-add` | `forEach(x -> list.add(x))` → `collect(…)` | — |
| `db-call-in-loop` | вызов репозитория, `EntityManager`, `JdbcTemplate` в цикле или стриме (N+1) → `findAllById`, `saveAll`, `IN (…)` | — |
| `remote-call-in-loop` | `RestTemplate`/`WebClient`/Feign или класс-обёртка над ними в цикле | — |
| `lazy-collection-in-loop` | геттер ленивой `@OneToMany`/`@ManyToMany` в цикле → `JOIN FETCH`, `@EntityGraph` | — |
| `find-all-in-memory` | `findAll()`, а затем `filter/count/anyMatch…` или цикл с условием → запрос с WHERE | — |
| `eager-collection` | `@OneToMany`/`@ManyToMany` с `FetchType.EAGER` | — |
| `transaction-remote-call` | HTTP-вызов внутри `@Transactional` — соединение с БД держится всё время запроса | — |
| `proxy-self-invocation` | `this.method()` у метода с `@Transactional/@Async/@Cacheable/@Retryable` — аннотация не сработает | — |
| `synchronized-bean` | `synchronized`-метод в `@Service/@Component/@Controller` | — |
| `regex-in-loop` | `Pattern.compile`, `String.matches/replaceAll` в цикле | — |
| `heavy-object-per-call` | `new ObjectMapper()/Gson()/XmlMapper()` в методе | — |
| `print-stack-trace` | catch, который только печатает `printStackTrace()` | — |

Для Big O стримы и лямбды считаются проходами по данным: конвейер — это цикл, а лямбда,
переданная в `filter/map/forEach/anyMatch/groupingBy/removeIf/…`, — его тело. Поэтому
`orders.stream().filter(a -> orders.stream().anyMatch(…))` даёт O(n²), как и вложенный for.
`map/filter/flatMap` у `Optional` (`repo.findById(id).map(…)`) циклом не считаются, коллекция в `for (x : items)` —
тоже: она вычисляется один раз.

Граф вызовов разрешает цель по типу получателя: поле, параметр, локальная переменная, имя класса, `super`; учитываются
наследники и реализации интерфейса. Если тип не из проекта (`List`, `String`, `JpaRepository`), ребра нет. Если тип
неизвестен, цель ищется по имени метода, как раньше.

## Поддержанный Java scope

### Бонусный уровень

| Конструкция | Что делает инструмент |
|---|---|
| `record` | компоненты record — поля модели; видны в дереве структуры; компактный конструктор — метод |
| `enum` | константы перечисления в дереве; конструкторы и методы enum — обычные методы; `switch` по enum |
| дженерики | параметры типа классов и методов (`Range<T extends Comparable<T>>`, `<T, R> mapAll(…)`) в дереве и обзоре |
| лямбды и `java.util.function` | каждая лямбда — отдельная блок-схема (выражение или блок), переход по ссылке «λ» из узла и вложенно в дереве; в обзоре — по переключателю; ссылки на методы `Order::id`, `TreeMap::new` попадают в граф вызовов |
| Stream API и `Collectors` | конвейер — узел «Поток» со списком стадий (`filter`, `map`, `collect(groupingBy…)`); у стадии с лямбдой — переход к её схеме; правила и оценка сложности выше |

### Зависимость от окружения

Многопоточность, рефлексия, файлы, сеть и `java.time` не моделируются, но **распознаются**:
программа с ними разбирается и показывается как обычно, а инструмент честно предупреждает.

| Категория | Что распознаётся |
|---|---|
| многопоточность | `java.util.concurrent`, `Thread`, `ExecutorService`, `CompletableFuture`, `synchronized`, `volatile`, `parallelStream()` |
| рефлексия | `java.lang.reflect`, `Class.forName`, `getDeclaredMethod/Field`, `setAccessible`, `newInstance` |
| файлы | `java.nio.file`, `Files`, `Path`, `File*` (консольный `System.in` — в рамках) |
| сеть | `java.net`, `Socket`, `URL`, `HttpClient` |
| время | `java.time`, `Date`, `Calendar`, `System.currentTimeMillis/nanoTime` |
| случайность | `new Random()` без seed, `Math.random()`, `UUID.randomUUID()` (в рамках, но ломает сравнение) |

Собственные классы проекта с такими именами (`class Date`) не считаются. В интерфейсе это пункты общего списка
проблем (важность «низкая», по одному на категорию в файле, с переходом к коду и пояснением, как это влияет
на проверку поведения) и метка на узлах блок-схемы.

**Проверка поведения.** Если в эталоне или текущей версии есть время, потоки, сеть или случайность,
эталон запускается на каждом тесте дважды. Когда он расходится сам с собой, тест помечается
«Недетерминировано», а не «Расхождение»: доказать сохранение поведения такого теста нельзя.
Программы выполняются во временном каталоге с таймаутом; сеть и файловая система не изолированы.

### Обязательный уровень

Разбор — полная грамматика Java 17+ (tree-sitter-java), включая record, enum, дженерики, лямбды, switch-выражения.
Блок-схема: последовательности, `if/else`, `for`, `for-each`, `while`, `do-while`, `switch` (старый и стрелочный,
с fall-through), `try/catch/finally`, try-with-resources, `break/continue` (в т. ч. с метками), `return`, `throw`.
Компиляция и запуск — настоящим `javac`/`java`, поэтому семантика проверяется на реальной JVM.
Проект с `pom.xml` собирает Maven. Проект без него (IntelliJ, Eclipse) собирается `javac`, а известные библиотеки
узнаются по импортам и скачиваются через Maven (`server/src/libs.ts`): JavaFX, Gson, Guava, Jackson, org.json,
commons-lang3/io, SLF4J, Lombok, JUnit, FlatLaf. Приложение JavaFX (`extends Application`) только компилируется:
оно открывает окно, и сравнение по stdin к нему неприменимо.

## Ограничения (текущий каркас)

- Перегрузки в графе вызовов не различаются; для лямбда-параметров и `var` без `new` тип получателя неизвестен,
  и цель ищется по имени метода.
- Типы переменных для правил — по объявлениям в методе и полям класса, без полного вывода типов.
- Узкие места и оценка вариантов распила — эвристики по коду, а не профилирование.
- Проект без `pom.xml` получает только библиотеки из таблицы в `server/src/libs.ts`; ресурсы (`.fxml`,
  `.properties`) не импортируются.
- Автоматических исправлений («Оптимизировать») и автодекомпозиции на файлы пока нет — следующий шаг.
- Сравнение stderr строгое: стектрейсы с другими именами классов после декомпозиции дадут расхождение.
- Песочница — отдельный процесс JVM с таймаутом и `-Xmx256m`, без изоляции файловой системы и сети.
