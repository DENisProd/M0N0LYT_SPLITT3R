# Dark Secrets

Веб-инструмент для работы с Java-монолитом. Загружает проект, строит по нему граф классов, вызовов и блок-схемы
методов, находит дефекты и оценивает сложность. Править код можно в графе или в редакторе. Исправления,
разделение классов и применение паттернов проверяются компиляцией и сравнением поведения с эталоном.
Исходные файлы на диске инструмент не меняет: результат скачивается отдельной копией.

## Запуск

### Что нужно установить

| Что | Зачем | Обязательно |
|---|---|---|
| Node.js 20+ и pnpm | сервер и клиент | да |
| JDK 17+ (`javac`, `java` в `PATH` или `JAVA_HOME`) | компиляция, запуск, сравнение поведения | да |
| Maven 3.9+ (`mvn` в `PATH` или `MAVEN_CMD`) | проекты с `pom.xml`, библиотеки для проектов без него, Mockito для тест-кейсов | для этих функций |
| [Ollama](https://ollama.com) с моделью (по умолчанию `qwen2.5:14b-instruct`) | исправления через LLM, применение паттернов, тест-кейсы от LLM | нет |

Без Ollama работают исправления по правилам, разделение класса, поиск паттернов и тест-кейсы по эвристикам.

Модель ставится один раз: `ollama pull qwen2.5:14b-instruct` (около 9 ГБ). Проверить окружение:
`node -v`, `pnpm -v`, `javac -version`, `mvn -v`, `ollama list`.

### Первый запуск

```bash
pnpm install           # корень: concurrently
pnpm install:all       # зависимости server/ и client/; postinstall генерирует клиент Prisma
pnpm dev               # миграции SQLite, сервер :3001 и клиент :5173
```

Откройте http://localhost:5173. Клиент проксирует `/api` на сервер, поэтому нужны оба процесса — `pnpm dev`
запускает их вместе. Первая сборка Maven-проекта скачивает зависимости в `~/.m2`, это может занять несколько минут.

Другие команды:

```bash
pnpm typecheck            # проверка типов сервера и клиента
pnpm build                # сборка клиента в client/dist
pnpm -C server start      # сервер без перезапуска при правках
pnpm -C server db:studio  # просмотр базы
```

## Интерфейс

- **Панель сверху** — импорт одного или нескольких `.java` («Импорт»), папки проекта («Проект»), демо-монолит
  («Пример»), «Экспорт копии», «Запуск», «Проверить поведение», статус JDK и эталона.
- **Слева** — файлы, дерево классов и методов, палитра блоков для вставки в метод.
- **В центре** — граф. Вкладки: «Приложения» (у проекта из одного приложения — «Схема», если код ходит в базы
  данных), «Границы» (только для нескольких приложений), «Методы», «Микросервисы», а также «Ревью» и разделение
  класса, когда они открыты.
- **Справа** — панель анализа: «Проблемы», «Паттерны», «Метрики».
- **Снизу** — код (Monaco) и панель: «Консоль», «Входные данные», «Тест-кейсы», «Результат», «Версии».

При импорте папки берутся `.java`, `pom.xml` и конфигурация (`application*.properties/yml`, `bootstrap*.yml`,
`persistence.xml`, `hibernate.cfg.xml`); пути пакетов сохраняются, тесты из `src/test` пропускаются. Загруженный код
сохраняется как первая версия «Исходная версия» и становится эталоном поведения. Настройки проекта (входные
данные, тест-кейсы, выбранный вариант разделения на микросервисы) хранятся в SQLite и восстанавливаются при повторной загрузке
того же проекта.

## Функции

### Граф и редактирование

<img width="1034" height="714" alt="image" src="https://github.com/user-attachments/assets/39c3a9ee-34e6-46d0-a019-0fadf6d7737f" />

Три уровня просмотра:
- «Приложения» — сервисы проекта, связи между ними (HTTP, Feign, брокеры сообщений) и хранилища данных, в которые
  они ходят. Приложение — модуль Maven, класс с `main` или `@SpringBootApplication`;
- «Границы» — классы внутри рамок своих приложений и вызовы через границы;
- «Методы» — обзор классов (методы, вызовы, сложность, число проблем) и блок-схема выбранного метода.

Клик по узлу подсвечивает его код, клик в коде выбирает метод и узел. Двойной клик по узлу открывает
редактирование его кода (Enter — применить, Shift+Enter — перенос строки, Esc — отмена). Блоки из палитры
вставляются после выбранного узла или в начало метода. Любая правка в редакторе сразу перестраивает граф.

Граф — проекция AST, а не отдельная модель. Каждый узел хранит диапазон исходника, и правка в графе — это
замена текста по этому диапазону. После неё код заново разбирается. Поэтому граф и код не расходятся, а
форматирование и комментарии вне правки сохраняются. Пока анализ не догнал правку, редактирование из графа
заблокировано.

### Диагностика

Вкладка «Проблемы»: дефект, место в коде, рекомендация и оценка сложности до и после исправления.

| Правило | Что ищет | Оценка |
|---|---|---|
| `nested-loops` | вложенные циклы; если внутри поиск по равенству — советует индекс HashMap | O(nᵏ) → O(nᵏ⁻¹) |
| `linear-search-in-loop` | `contains/indexOf/remove` у List внутри цикла | O(n²) → O(n) |
| `string-concat-in-loop` | `s += …` для String в цикле | O(n²) → O(n) |
| `empty-catch` | пустой catch | — |
| `long-method` | больше 40 строк (больше 80 — высокая важность) | — |
| `high-cyclomatic` | цикломатическая сложность больше 10 | — |
| `duplicate-block` | одинаковые блоки из 3+ операторов | — |
| `stream-sort-for-min` | `sorted(…)…findFirst()` ради одного элемента → `min(…)` | O(n log n) → O(n) |
| `stream-count-for-exists` | `count() > 0` / `== 0` → `anyMatch` / `noneMatch` | — |
| `stream-find-is-present` | `filter(…).findFirst().isPresent()` → `anyMatch` | — |
| `stream-foreach-add` | `forEach(x -> list.add(x))` → `collect(…)` | — |
| `db-call-in-loop` | вызов репозитория, `EntityManager`, `JdbcTemplate` в цикле или стриме (N+1) | — |
| `remote-call-in-loop` | `RestTemplate`/`WebClient`/Feign или обёртка над ними в цикле | — |
| `lazy-collection-in-loop` | геттер ленивой `@OneToMany`/`@ManyToMany` в цикле | — |
| `find-all-in-memory` | `findAll()` с последующей фильтрацией в памяти | — |
| `eager-collection` | `@OneToMany`/`@ManyToMany` с `FetchType.EAGER` | — |
| `transaction-remote-call` | HTTP-вызов внутри `@Transactional` | — |
| `proxy-self-invocation` | `this.method()` у метода с `@Transactional/@Async/@Cacheable/@Retryable` — аннотация не сработает | — |
| `synchronized-bean` | `synchronized`-метод в `@Service/@Component/@Controller` | — |
| `regex-in-loop` | `Pattern.compile`, `String.matches/replaceAll` в цикле | — |
| `heavy-object-per-call` | `new ObjectMapper()/Gson()/XmlMapper()` в методе | — |
| `print-stack-trace` | catch, который только вызывает `printStackTrace()` | — |

Для Big O стримы считаются проходами по данным: конвейер — цикл, лямбда в `filter/map/forEach/anyMatch/…` — его
тело. `orders.stream().filter(a -> orders.stream().anyMatch(…))` даёт O(n²), как вложенный for. `map/filter`
у `Optional` циклом не считаются.

Граф вызовов определяет цель по типу получателя: поле, параметр, локальная переменная, имя класса, `super`, с учётом
наследников и реализаций интерфейса. Если тип неизвестен, цель ищется по имени метода.

### Автоисправление

<img width="1278" height="712" alt="image" src="https://github.com/user-attachments/assets/5498a9b8-49c2-4b41-a259-2b18346348d3" />

Кнопка «Исправить» у проблемы или «Исправить всё» над списком. Ничего не применяется сразу: результат
открывается в ревью.

Исправления по правилам — точные замены в AST:

| Правило | Замена |
|---|---|
| `stream-sort-for-min` | `sorted(c).findFirst()` → `min(c)` |
| `stream-count-for-exists` | `count() > 0` → `anyMatch(…)`, `== 0` → `noneMatch(…)` |
| `stream-find-is-present` | `filter(p).findFirst().isPresent()` → `anyMatch(p)` |
| `string-concat-in-loop` | `StringBuilder` вместо `+=` |
| `regex-in-loop` | `static final Pattern` в классе вместо компиляции в цикле |
| `heavy-object-per-call` | `static final` поле вместо создания объекта при каждом вызове |
| `empty-catch` | `System.err.println(e)` в catch; меняет вывод в stderr, об этом есть пометка |

Остальное (`nested-loops`, `linear-search-in-loop`, `long-method`, `high-cyclomatic`, N+1 и т. д.) исправляет
локальная LLM, если включён переключатель «LLM». Модель переписывает метод целиком, после чего ответ проверяется:

1. разбор — ответ должен быть корректным Java;
2. компиляция всего проекта;
3. сравнение поведения с версией до правки на входных данных и тест-кейсах проекта.

Если проверка не прошла, ошибки компиляции или расхождения вывода уходят модели, и она пробует снова — до трёх
попыток. За один запуск переписывается до 8 методов. Ход работы виден на экране генерации: какой метод, какая
попытка, сколько прошло времени и почему предыдущая попытка не подошла. Генерацию можно отменить.

Если проект не собирается и без правок или JDK нет, ответ проверяется только разбором, и в ревью об этом
написано. Тесты покрывают не всё, поэтому правки LLM стоит прочитать.

### Ревью изменений

Показывает построчный diff по файлам. Каждый фрагмент принимается или отклоняется отдельно, есть кнопки
«Принять файл» и «Принять всё». Принятые фрагменты ложатся в рабочую копию в приложении.

<img width="1274" height="714" alt="image" src="https://github.com/user-attachments/assets/554aeadf-3258-4462-89f7-a34d1b6c7e9a" />

Разделение класса и применение паттерна открываются в ревью без выбора фрагментов: части такой правки зависят
друг от друга и по отдельности не скомпилируются, поэтому её можно только принять или отклонить целиком.

### Версии

Вкладка «Версии» в нижней панели работает как упрощённый git:
- число изменённых файлов относительно текущей версии; их можно посмотреть в ревью, частично откатить или
  отменить все правки;
- фиксация версии с описанием;
- список версий: просмотр изменений версии относительно родителя, восстановление, скачивание копии проекта
  в этой версии, «Сделать эталоном» — сравнивать поведение с этой версией.

Версии хранятся в SQLite: содержимое файлов адресуется хешем и не дублируется между версиями.

### Экспорт копии

«Экспорт копии» скачивает zip с проектом в текущем состоянии: папка `<имя>-fixed`, та же структура каталогов,
что у импортированной папки. Изменённые и новые файлы — с текущим кодом, остальные — байт в байт как на диске,
включая файлы, которые не анализируются (ресурсы, `pom.xml`). Копия любой версии скачивается из списка версий.

### Проверка поведения и тест-кейсы

«Проверить поведение» запускает эталон и текущую версию на одних и тех же входах и сравнивает stdout, stderr и код
выхода. Входы задаются во вкладке «Входные данные» (stdin). «Запуск» компилирует и выполняет программу на первом входе.

Вкладка «Тест-кейсы» — вызовы методов класса с аргументами. Кейсы генерируются эвристиками (граничные значения,
пустые коллекции, null) и, по желанию, локальной LLM; зависимости заменяются заглушками Mockito. Кейсы можно
править. При проверке результаты вызовов на эталоне и текущей версии должны совпасть. Для Spring Boot и JavaFX,
которые по stdin не запускаются, сравниваются только тест-кейсы.

Если в коде есть время, потоки, сеть или случайность, эталон на каждом тесте запускается дважды. Если он
расходится сам с собой, тест помечается «Недетерминировано», а не «Расхождение».

### Хранилища данных

Анализ находит, в какие базы и другие хранилища ходит код, и показывает их на схеме приложений рядом с
внешними HTTP-сервисами и брокерами. Клик по хранилищу — адрес (с переходом к строке конфигурации), таблицы,
сколько к каждой обращений и записей, список мест в коде.

| Вид | Как определяется |
|---|---|
| SQL (PostgreSQL, MySQL, Oracle, H2, SQLite…) | `@Entity`/`@Table`, репозитории Spring Data JPA/JDBC/R2DBC, `JdbcTemplate`, `NamedParameterJdbcTemplate`, `JdbcClient`, `EntityManager`, `DriverManager` и `Connection/Statement` |
| MongoDB | `@Document`, `MongoRepository`, `MongoTemplate`, `MongoCollection` |
| Redis | `RedisTemplate`, `StringRedisTemplate`, Jedis, Redisson, Lettuce |
| Elasticsearch | `@Document(indexName)`, `ElasticsearchRepository`, `ElasticsearchOperations`, клиенты Elasticsearch |
| Cassandra | `CassandraRepository`, `CassandraTemplate`, `CqlSession` |

**Какое это хранилище.** Адрес берётся из `spring.datasource.url` (и аналогов для R2DBC, Quarkus, JPA),
`spring.data.mongodb.*`, `spring.data.redis.*`, `spring.elasticsearch.uris`, `spring.cassandra.*` или из строки в
`DriverManager.getConnection("jdbc:…")`. У `${DB_URL:jdbc:…}` берётся значение по умолчанию. Базовый
`application.*` важнее профилей (`application-dev.yml`). Хранилища сравниваются по движку, хосту и имени базы
без учёта регистра и параметров: если несколько приложений указывают один адрес, на схеме одна база, и связи к ней
идут от каждого приложения. Если адреса нет, обращения сводятся к единственному известному хранилищу того же
вида, а если известных нет — к одному узлу «адрес не найден».

**Таблицы.** Имя — из `@Table(name)`, `@Document(collection/indexName)`, иначе имя класса в snake_case (как
по умолчанию в Spring Boot). Обращения через репозиторий относятся к таблице его сущности. Текст SQL и JPQL
(`@Query`, `createQuery`, `createNativeQuery`, аргументы `JdbcTemplate`) разбирается: таблицы после `FROM`, `JOIN`,
`INTO`, `UPDATE`, имена сущностей JPQL переводятся в таблицы. Строки собираются из литералов, текстовых блоков,
конкатенации и `static final`-констант. Чтение или запись — по SQL (`SELECT` или `INSERT/UPDATE/DELETE`) или по
имени метода (`save`, `delete` — запись; `find`, `get`, `count` — чтение).

### Микросервисы

<img width="1470" height="790" alt="image" src="https://github.com/user-attachments/assets/e21551e3-3a33-410a-9d28-d3ba21a8f3d3" />

Вкладка «Микросервисы» строит граф зависимостей классов. Веса связей: наследование и generic-аргументы — 4, поле — 3,
вызов метода — 1, тип параметра или результата — 1. Роли классов (сущность, репозиторий, контроллер, слушатель,
сервис, DTO, конфигурация) определяются по аннотациям Spring/JPA и по имени. Конфигурация и точка входа копируются
в каждый сервис и не делятся.

Варианты разреза:
- **по сущностям** — `@Entity` и то, чем она владеет (`@OneToMany`, `@OneToOne`, `@Embedded`, `@ElementCollection`),
  плюс её репозиторий и классы с тем же доменным именем;
- **по API** — группы контроллеров и слушателей с общим доменным именем;
- **по связности** и **крупные сервисы** — сообщества графа (Louvain, разрешение 1 и 0.5); классы с общим доменным
  именем (`Order`, `OrderController`, `OrderService`) держатся вместе, иначе алгоритм режет по слоям;
- **по пакетам** — только если пакеты функциональные, а не слоистые (`controller`, `service`, `repository`).

DTO и исключения, которыми пользуются несколько сервисов, выносятся в общий модуль. Для каждого варианта
считаются доля связей внутри сервисов, модулярность (Newman), циклы между сервисами (Тарьян), общие сущности,
доля кода в самом крупном сервисе и вызовы, которые после разделения станут API или событиями.

**Данные.** Вместе с классами делятся и хранилища — у каждого сервиса своя база (`order-db`, `payment-db`)
с его таблицами. Таблица достаётся сервису, в котором лежит её сущность; таблица без сущности — тому, кто больше
в неё пишет, затем — больше обращается. На графе база сервиса стоит внутри его рамки, к ней идут рёбра от классов,
которые с ней работают. Обращение к таблице другого сервиса — оранжевое пунктирное ребро, а таблица в узле
базы помечена `⇄`. Для варианта выводятся:
- общие таблицы: владелец, почему он, кто ещё читает или пишет и из каких мест кода. Запись в чужую таблицу нужно
  перевести на API владельца, чтение — на API или копию данных по событиям;
- запросы, которые соединяют (`JOIN`) таблицы разных сервисов: после разделения одним SQL их не выполнить;
- хранилища без таблиц (Redis) не делятся: если ими пользуются несколько сервисов, они помечены как общие.

Оценка 0–100 эвристическая: 50 × связность + 50 × модулярность / 0.6. Штрафы: 12 за цикл, 5 за общую сущность,
6 за каждую транзакцию, которая станет распределённой (не больше 18), 4 за чужую таблицу, в которую пишут
(не больше 12), 4 за JOIN через границу (не больше 12), 20 — если в одном сервисе больше 70% кода.
Приложение меньше 8 связанных классов не режется.

#### Узкие места монолита

### Разделение класса

Разделение большого класса на несколько классов в том же пакете (Extract Class). Открывается кнопкой с ножницами
у класса в дереве слева или из находки «Большой класс» во вкладке «Паттерны».

**План.** Сервер строит его без LLM. Члены класса — вершины графа, рёбра — обращения метода к полю, вызовы между
методами и общие слова в именах. Агломеративная кластеризация делит переносимые члены на N − 1 групп. Число классов
предлагается по размеру класса, его можно поменять от 2 до 6. Оно включает исходный класс.

В исходном классе остаются члены, которые нельзя перенести без правки другого кода: конструкторы, `main`,
переопределения (`@Override`), члены с аннотациями, поля, которые инициализирует конструктор, не-private поля
экземпляра и методы, которые вызывают из других классов через объект. В плане они помечены замком с причиной.
Остальные члены можно перекладывать между классами вручную, имена новых классов можно поменять.

**Перенос.** Обращения переписываются так:
- статический член → `Part.x`;
- член экземпляра → через поле `final Part part = new Part(this)` в исходном классе, обратные обращения — `owner.x`,
  между новыми классами — `owner.otherPart.x`;
- вложенные типы исходного класса → `Main.Nested`, создание внутреннего класса → `owner.new Inner()`;
- `private` снимается только с членов, к которым после переноса обращаются из другого класса;
- статические обращения из других файлов проекта, включая `import static`, переписываются тоже.

После переноса проект компилируется и сравнивается по тестам с версией до разделения. Тест-кейсы перенесённых
методов не прогоняются: они вызывают метод у исходного класса, где его больше нет. Об этом есть пометка.

### Паттерны проектирования

Вкладка «Паттерны» на панели анализа. Поиск идёт по AST, без LLM.

**Уже в коде** — найденные паттерны и роли участников:

| Паттерн | Признак |
|---|---|
| Singleton | все конструкторы private, статическое поле и статический метод своего типа; enum с единственной константой `INSTANCE` |
| Builder | метод `build()` и 2+ метода, возвращающих `this` |
| Factory Method | метод возвращает супертип и создаёт 2+ разных его реализации |
| Strategy | класс хранит в поле интерфейс или абстрактный класс, у которого 2+ реализации |
| Command | то же, но интерфейс называется `*Command/*Action/*Task` или его единственный метод — `execute/run/perform/undo` |
| Observer | коллекция объектов интерфейса в поле, которую обходят и вызывают метод у каждого |
| Decorator | класс реализует интерфейс, получает объект того же интерфейса в конструкторе и хранит в поле |
| Template Method | абстрактный класс, в котором обычный метод вызывает абстрактные |

У Singleton проверяется ленивая инициализация: без синхронизации или при двойной проверке без `volatile` выводится
предупреждение и кнопка «Исправить».

**Можно применить** — места, где паттерн упростит код:

| Находка | Признак | Предложение |
|---|---|---|
| Ветвление по типу | `switch` или цепочка `if/else if` по одному значению (`equals`, `==` с константой, `instanceof`), 3+ ветки, 10+ строк | Strategy или полиморфизм |
| Создание по условию | в каждой из 3+ веток создаётся объект своего класса | Factory Method |
| Длинный конструктор | 5+ параметров или 3+ конструктора | Builder |
| Большой класс | больше 400 строк или больше 25 методов | разделение класса |

У каждой находки есть справка: назначение паттерна, когда он уместен и когда нет, код до и после. Внизу вкладки —
справочник по всем паттернам.

«Применить» передаёт класс и метод локальной LLM с инструкцией для конкретного паттерна. Модель возвращает новый
текст метода и новые члены класса (вложенный интерфейс и реализации, класс `Builder`), которые добавляются в конец
тела класса. Новые файлы не создаются, существующие конструкторы и сигнатуры не меняются. Проверка та же, что у
автоисправления: разбор, компиляция, сравнение поведения, до трёх попыток с ошибками.

### Зависимость от окружения

Многопоточность, рефлексия, файлы, сеть и время не моделируются, но распознаются: такая программа разбирается
как обычно, а в списке проблем появляется пункт низкой важности с пояснением, как это влияет на проверку поведения.

| Категория | Что распознаётся |
|---|---|
| многопоточность | `java.util.concurrent`, `Thread`, `ExecutorService`, `CompletableFuture`, `synchronized`, `volatile`, `parallelStream()` |
| рефлексия | `java.lang.reflect`, `Class.forName`, `getDeclaredMethod/Field`, `setAccessible`, `newInstance` |
| файлы | `java.nio.file`, `Files`, `Path`, `File*` (`System.in` не в счёт) |
| сеть | `java.net`, `Socket`, `URL`, `HttpClient` |
| время | `java.time`, `Date`, `Calendar`, `System.currentTimeMillis/nanoTime` |
| случайность | `new Random()` без seed, `Math.random()`, `UUID.randomUUID()` |

Собственные классы проекта с такими именами (`class Date`) не учитываются.

## Поддержка Java

Разбор — полная грамматика Java 17+ (tree-sitter-java). Блок-схема строится для последовательностей, `if/else`,
`for`, `for-each`, `while`, `do-while`, `switch` (обычного и стрелочного, с fall-through), `try/catch/finally`,
try-with-resources, `break/continue` с метками, `return`, `throw`.

| Конструкция | Как показывается |
|---|---|
| `record` | компоненты — поля модели; компактный конструктор — метод |
| `enum` | константы в дереве, конструкторы и методы — обычные методы |
| дженерики | параметры типа классов и методов в дереве и обзоре |
| лямбды | у каждой своя блок-схема, переход из узла по ссылке «λ»; ссылки на методы (`Order::id`) попадают в граф вызовов |
| Stream API | конвейер — узел «Поток» со списком стадий; у стадии с лямбдой — переход к её схеме |

Компиляция и запуск — настоящими `javac`/`java`. Проект с `pom.xml` собирает Maven. Проект без него собирается
`javac`, а известные библиотеки определяются по импортам и скачиваются через Maven (`server/src/libs.ts`): JavaFX,
Gson, Guava, Jackson, org.json, commons-lang3/io, SLF4J, Lombok, JUnit, FlatLaf. Приложение JavaFX только
компилируется: оно открывает окно, и сравнивать его по stdin нельзя.

## Ограничения

- Перегрузки в графе вызовов не различаются. Для лямбда-параметров и `var` без `new` тип получателя неизвестен,
  цель ищется по имени метода.
- Типы переменных для правил берутся из объявлений в методе и полей класса, полного вывода типов нет.
- Узкие места, оценка вариантов микросервисов и поиск паттернов — эвристики по коду. Возможны ложные находки и пропуски.
- Хранилища ищутся по типам клиентов и тексту запросов. SQL, собранный во время работы (из переменных, через
  билдеры запросов, jOOQ, Criteria API), не разбирается: обращение видно, таблица — нет. Несколько datasource
  в одном приложении сводятся к первому найденному адресу.
- Проверка поведения доказывает совпадение только на заданных входах и тест-кейсах. Чем их меньше, тем внимательнее
  нужно читать правки LLM в ревью.
- Качество исправлений и паттернов зависит от модели. На `qwen2.5:14b-instruct` одна попытка занимает от 30 секунд
  до нескольких минут.
- Разделяются только классы верхнего уровня; интерфейсы, enum и record — нет.
- stderr сравнивается строго: стектрейс с другими именами классов после разделения даст расхождение.
- Проект без `pom.xml` получает только библиотеки из `server/src/libs.ts`. Ресурсы (`.fxml`, `.properties`)
  не анализируются, но попадают в экспорт копии.
- Программы выполняются в отдельной JVM с таймаутом и `-Xmx256m`. Файловая система и сеть не изолированы.
